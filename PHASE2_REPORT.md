## 4–5. OpenAI API and model

Installed `openai` 7.23.0 and Zod. Uses `responses.create`, `input_file` base64 PDF bytes, `store: false`, strict `text.format` generated by `zodTextFormat`, and official SDK types. The response must be completed, non-refusal and valid against the strict Zod contract before internal persistence. Unknown fields cannot introduce executable state.

The centralized default is `gpt-4.1-mini`, overridden by the Convex deployment's `OPENAI_EXTRACTION_MODEL`. It supports image input, Responses and Structured Outputs and is suitable for a bounded low-cost extraction baseline; no quality benchmark is claimed. Official documentation checked: [PDF inputs](https://developers.openai.com/api/docs/guides/file-inputs), [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs), [model capabilities](https://developers.openai.com/api/docs/models/gpt-4.1-mini).

## 7. Upload architecture

An authenticated mutation creates an owner-bound, ten-minute upload ticket tied to a SHA-256 token digest. The browser sends the PDF directly to a Convex HTTP action with the raw 256-bit capability token in a header. That action checks MIME, actual streamed size (10 MiB maximum), and PDF signature; stores the Blob in Convex File Storage; and attaches the storage ID internally. Only the owner can register the ticket as an inspection. No API lets a client register an arbitrary storage reference. Unregistered attached files and tickets are cleaned after fifteen minutes.

This is a deliberate security variation from the preferred raw `generateUploadUrl()` approach: a bare storage ID and storage metadata do not establish uploader ownership. No permanent storage URL is stored or exposed. PDF bytes go directly from the server-side storage read to OpenAI.

## 8. Extraction schema

Document: nullable inspection type, site name/date and summary. Up to 40 findings: title/description, nullable category/location/requirement/recommended action, enumerated severity, HIGH/MEDIUM/LOW model-assessed confidence, and source `{ page: positive integer | null, section: string | null, excerpt: nonblank string ≤ 400 characters }`. All keys are required in model output; missing values use null; objects are strict. Convex validators and Zod checks reject malformed content before database writes.

## 9. Human review

Proposals are explicitly non-authoritative. Each card shows evidence and confidence, with low confidence highlighted. Edits preserve the original proposal, append before/after events, and remain PROPOSED until separately confirmed. Confirm/reject decisions are attributable to the authenticated owner and retained. Review counts update through Convex subscriptions. Empty/no-deficiency and all-rejected reports need explicit review completion; neither implies compliance.

## 10. Graph creation

Only CONFIRMED findings can create graphs, enforced in both backend creation APIs. A finding's graph ID is committed atomically with graph creation. Batch requests require completed inspection review and exclude rejected findings. Repeats return existing graph IDs. The fixed HUMAN template is requirement review → corrective-action coordination → evidence attestation → verification. Existing engine functions establish readiness and gate resolution. No model-generated graph or system final verification exists.

## 11. Security and recovery

Ownership is derived from Convex Auth on every public domain operation. Internal-only action callbacks cannot be invoked by clients. Upload capabilities are single-use, bounded and owner-bound; raw storage references cannot be claimed through public registration. Filename text is sanitized and rendered as text; the provider gets a fixed neutral filename. PDF instructions have no execution authority and no tools are supplied to the model.

Active run numbers plus transactional claims and persistence guard duplicate/stale callbacks. Safe retries are allowed only after failures or before analysis; reviewed data is never overwritten by reanalysis. SDK timeout is two minutes, automatic provider retries are disabled, and a separate five-minute watchdog recovers stranded analyses. User-visible errors are allowlisted. Operational diagnostics contain stage, HTTP status and bounded error code/category only, never provider messages, PDF payloads or secrets.
